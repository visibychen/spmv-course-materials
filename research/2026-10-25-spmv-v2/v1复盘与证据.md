# v1 差在哪里：从测量事实到 v2 约束

以下性能数字全部来自 [v1 正式记录](../../experiments/2026-10-25-v1/README.md)，不是 v2 新实测。完整计算、输入 SHA-256 和对象代码对照见 `diagnosis.json`。

## 1. 首要问题是短期总成本，不是“没有生成更宽 SIMD”

超大矩阵、24 线程、R=9：

| 项目 | 原始 | SELL16 |
| --- | --- | --- |
| 单次内核中位数 | 87.648 ms | 85.355 ms |
| 准备中位数 | 0 | 397.570 ms |
| 准备+执行中位数 | 0.788833 s | 1.173283 s |

SELL16 内核中位数只快约 2.62%（加速比 1.027×），准备+9次却慢约 **48.74%**。若沿用这组单次中位数：

```text
每次节省 = 87.648111 − 85.354667 = 2.293444 ms
R=9 可抵消的最大准备成本 = 9 × 2.293444 = 20.641 ms
实际准备 / 可抵消准备 = 397.570 / 20.641 ≈ 19.26
模型中严格回本的最小调用次数 = 174
```

这不是说 R=174 一定回本。独立 R=100 测量的单次耗时不同，实际含准备中位数已出现约 1.053×；它说明缓存、频率、同步占比和样本波动会改变 T。不能把一组 R=9 的 T 外推成普遍阈值，也不能用 R=100 的 T 回填 R=9。

如果准备成本仍为 397.570 ms，R=9 下新内核必须降至约 **43.474 ms/次** 才能追平该模型的原始时间，约为 v1 SELL16 耗时的一半。仅仅把转换改成多线程，并没有证据保证跨过这个门槛。

**对 v2 的约束**：短调用优先避免整份格式转换；优化是否成立看准备+执行，而不只看内核。

## 2. 源码中确实存在的准备工作与空间成本

核查 v1 `spmv_plan.c`：独立检查行指针和全部列号；统计各 slice 最大行长；分配派生数组；再次计算宽度并串行填充。`main.c` 在 OpenMP 执行区域之前串行调用 prepare。上述是代码事实；各阶段占多少毫秒尚无独立计时，不能直接断言“某一次扫描占了大多数时间”。

无转换的 csr-scalar 在超大矩阵、24 线程下也需要约 38.605 ms 准备，包含合法性检查。这已大于 SELL16 在 R=9 的约 20.641 ms 预算。不能以直接删检查解决；应考虑在已需要遍历的合法构造过程中合并验证、保存失效版本，并把新增验证成本仍计入总耗时。

SELL16 复制的额外数组为 **774,000,008 B，约 738.14 MiB**。原 CSR 仍存在；全程峰值 RSS 接近原始版本，是因为峰值可能更早出现在 COO+CSR 共存阶段，不能解释为没有额外驻留内存。

代码还有一个局部效率问题：`full_slices` 是全局标志，一个不等长 slice 或部分尾块会让整个矩阵走带掩码路径。它值得独立消融，但尚未测得其时间贡献；例如 random4 的行数可被 C 整除，不能用尾块掩码解释这个用例的退化。

## 3. 内核选择依赖输入，不能统一选 SELL 或 pack

| v1 条件 | 观察 | 可以支持的结论 |
| --- | --- | --- |
| 超大矩阵、1 线程 | original 740.438 ms，scalar 582.174 ms，pack 828.016 ms | 手动 pack 对当前短行随机输入可能更慢 |
| random8、12 线程 | SELL8 2.082 ms，scalar 2.156 ms；SELL16 2.259 ms | SELL 对最强 CSR 对照的优势远小于对原始的表面优势 |
| random4、12 线程 | SELL16 中位耗时约为原始的 1.102× | 存在退化中位数，但区间重叠，不宜宣布已证明稳定退化 |
| 集中长尾、12 线程 | SELL16 相对原始约 1.734×，相对 pack 约 1.217× | 跨行布局对这个构造有效，不能外推为所有长尾有效 |
| 百万元素巨行、12 线程 | pack 约 2.329×；1→24 线程并未稳定变快 | 行内多累加器有用，但整行仍只由一个线程负责 |

SELL 没有消除 `x[j[k]]` 的间接访问。当前没有实际 DRAM 流量和持续带宽上限，不能声称已经“打满带宽”，也不能把 24 线程优势小直接归因于 AVX-512 降频。

## 4. 行数均分在集中长尾上很差，但空行多不一定失衡

按原输入生成器、GCC 常见连续静态行划分复算工作量；结果是**结构模型而非实测时长**。`max/mean nnz` 是最大线程 nnz 除以线程平均 nnz。

| 输入、24 线程 | 等行数分区 max/mean nnz | 按 nnz+rows 分区模型 | 判断 |
| --- | --- | --- | --- |
| 原超大均匀矩阵 | 1.000 | 1.000 | 本来已均衡，不能指望负载均衡加速 |
| 集中长尾 | 17.521 | 1.073 | 连续行工作量分区值得优先实现 |
| 分散长尾 | 1.006 | 1.008 | 本来接近均衡，分区不一定更好 |
| 单条巨行 | 21.909 | 21.818 | 整行分区仍受一条巨行下界限制 |
| 99% 空行、均匀散布 | 1.001 | 1.001 | 主要不是线程 nnz 失衡，不能直接判定应使用 merge |

`nnz+rows` 的 λ=1 是项目的成本近似，不是论文给出的通用最佳权重。事件数 / 非零元均衡也不等于线程实际耗时均衡；x 局部性与指令成本不同。

SELL 在巨行、分散长尾和 99% 空行中因为填充保护回退，防止了过量复制，但**并没有解决这些输入的计算瓶颈**。回退后某些中位数更快，不能记成 SELL 算法收益。

## 5. 小矩阵被并行与同步成本压倒

缓存内 256×256、2048 nnz、R=100：原始 1 线程约 0.0013 ms/次，24 线程约 0.3233 ms/次，精确比值约 **248.7 倍**。12 线程也约 0.1578 ms/次。

这表明当前设置下计算太少，增加线程得不偿失。PASSIVE 等待与逐次隐式屏障是有依据的解释方向 [R6]，但没有逐项计时，不能把全部差值认定为某一个 barrier 的纯成本。v2 应先比较真正串行路径；不能靠只给新版本切 ACTIVE、却保留原始 PASSIVE 来制造内核收益。

## 6. 实验归因还不够强，v2 要先加强对照

同为超大矩阵、24 线程、R=9：原始二进制的 original 中位数为 87.648 ms，新二进制的 original 路径为 101.296 ms，相差约 **15.57%**，且两者极差重叠。这比 SELL16 相对原始约 2.62% 的内核节省更大。

本轮附加核查：两个构建的 `csr.c` SHA-256 相同，`csr.o` 的 `.text` 字节也相同（24,786 B，哈希见 JSON）。这不保证最终链接地址、缓存状态、包装或运行环境相同，但说明不能把 15.57% 直接解释为 CSR 算法变差，更不能断言分派函数就消耗了这些毫秒。

v2 同时需要同二进制内核对照和原始独立程序的工程对照，主条件增加相邻随机配对与样本；保留极差和区间，避免仅凭几个中位数选择策略。原始历史 baseline 不改写。

## 7. 适用范围与数值代价

v1 只优化 f32/f32/f32，其他类型回到原始；pack 改变归约结合顺序，SELL 的显式乘加与原始尾部也可能不同。准备计划借用 CSR 并保存 SELL 快照，矩阵更新后必须重建。v2 不应以放宽精度、缓存 Ax、改少调用次数或省掉必要同步替代真正的 SpMV 改进。

本轮得到的是“哪里值得做、哪里不能保证”的约束，没有产生新的 v2 加速数据。来源编号见 [资料与复用索引](资料与复用索引.md)。

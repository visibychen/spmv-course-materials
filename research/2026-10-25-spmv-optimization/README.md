# SpMV 优化调研与方案 v1

调研日期：2026-10-25。对象：原始 `csrspmv`，版本 `9352c865044f4c8b344d6fe5a277200a89f7a08b`；本机 WSL2、GCC 11.4、Ryzen 9 7845HX。此次工作是文献与源码调研、适配分析和实验设计，**尚未实现或测得新的算法加速**。

## 先回答：已有 CSR、OpenMP 和自动向量化，还能优化什么？

它们分别解决了压缩存储、线程并行、指令并行的一部分问题；具体的工作划分、SIMD 通道分配、间接访存、转换成本和适用矩阵仍然存在选择空间。原始程序按行分配，f32 在一行内 gather/乘法，再用标量加法链归约；SELL-C-σ 可以把不同的行放进不同 SIMD 通道，merge-based 可以把超长行拆分到多个线程。这些是已有论文和实现提供的具体方法。

推荐路线：**保留原始 CSR 作为输入和回退路径 → 小范围 CSR 内核对照 → SELL-C-σ 跨行 SIMD → 不规则矩阵的工作量划分 / merge-based 扩展**。重排和缓存分块作为针对有结构矩阵的后续分支。

这不是“所有方法一起堆上去”的实现清单。第一轮交付聚焦 CSR 对照与无排序 SELL；后续阶段由正确性、实测收益、预处理回本次数决定是否进入。

## 本次最值得直接复用的资料

1. [SELL-C-σ 原论文](https://arxiv.org/html/1307.6209) 与 [GHOST 作者团队实现](https://github.com/RRZE-HPC/GHOST)：跨行 SIMD 的主要依据。

4. [原作者 SC23 软件归档](https://zenodo.org/records/7837264)：CSR、ELLPACK 和 `mtxreorder` 工具，可直接复现既有方法；归档中的 double 内核和测法需适配当前 f32。

全文没有把论文中的倍数、另一台机器的吞吐或已有 OpenMP 的线程扩展倍数，写成本项目预计或已取得的收益。

## 已完成的分析计算

`feasibility_analysis.py` 根据原矩阵元数据计算：当前输入 C=8 /16 的数据槽填充倍率都是 1；但在“一条百万项长行 + 七条单项行”的反例中，C=8 的倍率约为 8。另一个混合行长例子中，局部排序可以把倍率从约 3.95 降至 1。这些是存储公式的结果，不是速度测试。

若原 CSR 保留，采用 f32 / int32 数据、int64 slice 指针及宽度、不存均匀行的额外映射，当前 C=8 /16 的 CSR+SELL+x+y 估算分别约为 1.752 /1.740 GB；还未计分配器、检查与调参临时空间。这说明“填充倍率为 1”也不等于“额外内存为 0”，最终峰值须实测。
